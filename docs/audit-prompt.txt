You are auditing Armada file-by-file toward an immaculate result. I will provide one or more files to examine.
Report findings first; after I approve them, apply the fixes, verify, and commit. This is an audit-AND-fix pass,
not read-only. AGENTS.md is the architecture standard; this file is the audit procedure. Where they overlap,
AGENTS.md wins.

## Workflow

- **Findings first, then fix.** Report findings before touching anything; make NO edits until I approve specific
  findings. After approval: apply, verify, and commit when I say.
- **Verify, don't guess.** Search the codebase to confirm cross-file claims (consumers, dead code, duplication,
  import conventions) BEFORE finalizing a finding or making a change. Resolve "needs verification" by checking;
  only ask when the code genuinely can't answer it.
- **Fix as found; don't defer.** When a fix crosscuts other files (not-yet-audited, already-audited, or shared),
  make it now. Don't park work in TODOs or memos. The goal is that a later file is already clean when we reach it.
- **Verify before deleting.** For dead code TypeScript won't flag (object/map members, query keys, string-keyed
  config, barrel re-exports), grep all usages first; zero consumers = dead (caller-first). When deleting a file or
  barrel, grep EVERY import form: relative (`./x`, `../x`), aliased (`@renderer/x`, `@main/x`, `@shared/x`), AND
  `export *` re-export chains. A partial-path grep misses re-exporters.
- **A "DRY" swap can change behavior.** Replacing inline logic with a shared helper or type may differ on edge
  cases. Diff the two implementations and flag the behavior change; don't present it as behavior-neutral.
- **No tests = the diff is the gate.** When a refactor touches behavior-sensitive code with no test coverage,
  "tests pass" is vacuous. Gate on a careful per-item diff trace plus typecheck, and note the missing coverage in
  the finding.
- **Decide by convention, with data.** When choosing to keep, remove, or standardize a pattern (barrels, accessors,
  naming), measure the dominant convention with grep counts instead of assuming. Keep what's the real import
  surface; remove what's vestigial.
- **Immaculate = no dead weight AND no un-consolidated duplication. Be decisive.** Clean, behavior-neutral wins
  that clear the bar (two or more identical callers with an existing precedent, a grep-proven dead export) are not
  "optional". Apply them; don't hand a clean call back as "your call." Reserve genuine consultation for real
  judgment: over-abstraction risk, a behavior or visual change, or a large multi-file refactor. Present those and
  get explicit sign-off.
- **Be specific.** Exact line numbers and code, with confidence levels (high / medium / needs-verification).
- **Gate on green.** After changes, run `npm run typecheck`, `npm run lint`, and `npm test` and report results.
  Don't claim done without them.

## What to look for

### 1. Comments

Zero comments. No file headers, no JSDoc, no docstrings, no section banners, no line narration, no TODOs, no
commented-out code. The code documents itself through naming.

Sole exception: one line containing `PITFALL:` for something a reader genuinely cannot infer from the code (a
workaround, a spec quirk, a silent failure, an intentional overwrite).

Flag for removal:
- Any comment that is not a `PITFALL:` line.
- A `PITFALL:` line that restates what the code already shows. The bar is "a careful reader would get this wrong
  without it."
- A bare `eslint-disable` without a `-- reason`. A disable sitting on code the rule can no longer fire on is dead.

Self-documenting code check: if a comment exists only to compensate for a poor name, the naming is the real
finding. Rename; don't just delete the comment.

Never flag a missing file header.

### 2. File Naming & Organization

The naming table, entity-first component pattern, established suffixes, and `ui/components/` subdirectory rules
live in AGENTS.md. Audit against those; don't restate them here.

Flag these issues:
- File name doesn't match what the file exports or does (a file named `helpers.ts` that only contains layout math
  should be named for the layout math).
- File name uses the wrong casing convention for its type (a hook file in PascalCase, a component file in
  camelCase).
- Generic or vague file names: `utils.ts`, `helpers.ts`, `misc.ts`, or a barrel `index.ts` that re-exports nothing
  meaningful.
- File sits in the wrong directory for what it does (a component in `utils/`, a hook in `components/`, a pure edit
  function outside `model/`).
- File mixes unrelated concerns (a component and an IPC helper in one file).
- Inconsistency with sibling files in the same directory.
- Directories named after UI patterns (`modals/`, `forms/`) instead of features (`grid/`, `sidebar/`).
- Default exports. Named exports only.

Loose files:
- Flag files sitting directly in a directory when every sibling entry is a subdirectory, except `index.ts`.
  Move them into the most appropriate existing subdirectory, or a new one if none fits.
- When recommending a move, check what already imports the file. The import path change is part of the finding.

### 3. Boundaries

The specific rules are in AGENTS.md (Process Boundary, Shared Schemas, Cross-Layer Imports, No Parallel Systems).
Audit every file against them:

- A shape that crosses main/renderer defined anywhere other than `src/shared`. A hand-rolled interface that
  overlaps a shared schema type instead of `z.infer`.
- A Zod schema nothing calls `.parse()` on. A `.parse()` on in-process output (validation theater).
- A string-literal channel name instead of a constant from `@shared/ipcChannels`.
- An inbound IPC handler that reaches a service or repository without parsing its payload first.
- `app.getPath`, `os.homedir()`, or a `~/.claude` path built anywhere other than `main/infrastructure/paths.ts`.
- `pty.spawn` outside `PtySessionHost`. A session spawned from a shell string instead of an argv array.
- `domain/` importing Electron, Node built-ins, or `infrastructure/`.
- Renderer importing from `src/main`. A renderer domain importing another domain's internals instead of its
  `index.ts` surface.
- Main-owned data (conversations, workspace) held in a Zustand store. Pty output held in React state.
- A workspace save that bypasses `useWorkspaceEditor().edit`.
- Error text rewritten in the renderer instead of shown verbatim through `getErrorMessage`. A toast from anywhere
  other than the `MutationCache.onError` in `queryClient.ts` or the session-open path in the terminal hook.
- `null` used for an optional value.

### 4. Duplication

- Logic duplicated WITHIN the file (similar blocks, repeated patterns that could be consolidated).
- Logic duplicated ELSEWHERE. Verify by searching, then consolidate to a shared home. Before extracting, confirm
  at least two real callers; a helper with one caller gets inlined.
- Magic strings and keys duplicated across files (query-key roots, colors, grid constants, storage keys). Centralize
  to a single owner: `@renderer/app/queryKeys`, the design tokens in `app/styles`, the grid constants where the
  layout lives.

### 5. Technical Debt

- Overly complex logic that could be simplified.
- Inconsistent patterns (mixing async styles, inconsistent error handling).
- Magic numbers and strings without a name. Numbers inside a named-key config object are self-documenting; flag
  standalone literals that recur or carry meaning.
- Redundant type annotations the initializer already fixes (`x: boolean = false`). Keep ones that widen on purpose
  (`Set<string>` so `.has(someString)` typechecks against a literal union).
- Redundant parameters always passed the same module singleton (a `queryClient` param that's always the imported
  instance). Drop the param, use the import.
- Thin wrappers that only forward to a store action, prop, or sub-object (`const handleX = () => clearX()`,
  `getColumn()` returning `tile.position.column`). Pass the action or reach in directly.
- Single-use components or helpers extracted only to shrink a file. Extract on genuine reuse or to isolate a
  cohesive, separable concern, not the interdependent core of a large component.
- Poor naming that obscures intent. A method name that restates its parent (`boards.boardList()`).
- Props drilled through components when the child could call the hook directly.
- Missing error handling at a process boundary.
- A field added to a request, tile, or board that no layer reads at the bottom (spawn argv, JSON on disk, rendered
  output). Trace it end to end.
- `{ ...userInput, field: systemValue }` that silently discards the user's value without a `PITFALL:` line saying
  why.
- An interactive element with no keyboard path.

### 6. Dead Code

- Exported functions, variables, types, or schemas unused codebase-wide. Verify by grepping all consumers, not just
  this file.
- Speculative exports, keys, fields, props, channels, or handlers with zero PRODUCTION consumers. Something used only
  by a dev preview, mock, or test harness still counts as speculative.
- Barrels are a two-part decision. DELETE a barrel with zero external importers (everyone deep-imports it, so it
  isn't the real surface). KEEP-and-TRIM a barrel that IS the surface: re-export only the externally consumed
  symbols, drop the rest. Decide with grep counts, barrel-path imports vs deep-path imports. Each renderer domain's
  `index.ts` is meant to be its only public surface; a deep import into a sibling domain is a finding on the
  importer, not a reason to delete the barrel. A `*Props` interface used only in its own file → unexport it.
- Unreachable or constant-by-guard code paths: a branch hidden by an earlier broader check, a condition made
  always-true by an enclosing guard, an `else` unreachable because an upstream check returned.
- Variables assigned but never read. Imports not used in the file. Parameters no caller reads.
- Feature flags or conditional branches that appear permanently stale. The `kind` default for pre-kind tile files
  is intentional and stays.
- Completely unused files. A component can be exported through a domain barrel yet have zero real consumers.
  Confirm liveness by grepping the JSX render site (`<Name`) and every import site across the tree, not just "is it
  exported."

## Output Format

For each file, respond with:

File: <path>

Then list findings grouped by category. For each finding:
- Line(s): exact line number(s)
- Finding: what you observed
- Confidence: high / medium / needs verification
- Context needed (if any): what you'd need to see to confirm

If a file looks clean, say so. Don't manufacture findings.

## After Changes

Commit only when I say. Commits are batched by top-level directory, in this exact format:
audit: <directory scope> — <specific changes, comma-separated>

Collateral cross-cutting changes from a directory's audit ride along in that directory's commit; don't split them
out. No co-author footer. Before committing: gate on green (typecheck, lint, tests), then stage precisely and
exclude unrelated work in progress.

Examples:
- audit: renderer/domains/boards — inline single-caller lane width helper, remove dead reflow export, move grid
  constants to one home
- audit: main/ipc — parse session resume payload before service call, replace literal channel names with constants
- audit: shared — unexport internal TilePosition, drop schema with no parse call site

The directory scope stays consistent across related commits. Each commit message describes the specific changes
made in that pass.
